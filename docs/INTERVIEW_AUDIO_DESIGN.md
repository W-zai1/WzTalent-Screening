## 0. 先说这个功能不能做什么（项目传统：边界先于方案）

1. **面试表现 ≠ 工作表现**。结构化面试与工作表现的相关系数约 0.3–0.5，且受首因效应、对比效应等偏差影响。本功能产出「面试环节的证据整理」，**不是录用概率**。
2. **Panel 场景下“哪个面试官在说”是最佳努力，不是承诺**。角色分离（面试官 vs 候选人）可靠；面试官之间的身份区分（A/B/C）只有弱信号（自我介绍、点名、提问领域）。但这条边界**不影响候选人评分**——问题记错归属面试官，污染的是评估者元数据，不是对候选人的判断。所以设计上：角色分离必须准，面试官身份尽力为准，不准就归“面试官（未区分）”。
3. **ASR 与 OCR 的错误会向下游传播**。每层带置信度，未确认内容不进分析，覆盖率显式声明。
4. **录音与手写笔记都有法定义务**。录音含声纹（生物识别信息，PIPL 敏感个人信息，需单独同意）；面试官笔记属评价记录。系统提供阻断式提示，但不替代部署方的合规动作。
5. **只做事后分析，不做实时**。
6. **图片 OCR 依赖 WorkBuddy 视觉通道**。`docparse.parse_image` 当前只走 WorkBuddy 反代（glm-5v-turbo 等），其他 provider 下图片无法 OCR——已有优雅降级（提示“改成把文字直接粘贴进来”）。
7. **真正的群面（一个面试官 × 多个候选人）不在本期范围**。原因见 §3.4：无声纹方案下区分两个候选人没有可靠自动解，而错标会直接污染某个候选人的评分且无人察觉。要做需要先引入声纹 embedding，那是另一个量级的工程。

## 3. 核心设计：Panel 场景的说话人归属

### 为什么不用 pyannote / 声纹 embedding

torch 全家桶 + GPU + HF token，直接违反项目唯一硬约束（零第三方依赖）。且对面试场景是杀鸡用牛刀——见 §3.4。

### 3.1 三层归属（1:1 与 Panel 同一套机制）

Panel 相比 1:1 唯一的区别是“面试官”这一侧有多个人——但**归属问题是同一个二元问题**：这句话是面试官说的还是候选人说的。多个面试官只需聚类为同一角色，不需要互相区分也能完成核心任务。

| 层 | 做法 | Panel 场景的适配 |
|---|---|---|
| 层 1 问题对齐 | ASR 段落与面试通知里的已知问题清单做文本对齐，命中判为面试官 | 不变。结构化面试的场景红利：**面试官的话大半是提前写好的** |
| 层 2 LLM 言语行为归因 | 剩余段落按言语行为判定（介绍公司/谈薪/问经历 → 面试官；自述经历 → 候选人），输出 `{speaker, confidence, reason}` | 不变。Panel 里多位面试官的提问风格不同，反而更容易判“这是提问方” |
| 层 3 人工修正 | UI 逐段显示归属+理由+置信度，一键改，写审计，样本回流 | 不变 |

任何一层不确定 → 段落标 `unassigned`，UI 高亮，**不喂给分析层**。分析输出带“基于 X/Y 段确认内容”的覆盖率声明——结论的适用边界成为已知量（沿用上下文截断留痕的同款哲学）。

### 3.2 面试官身份区分：尽力为准，不准无损

Panel 的增益分析（谁问了什么、哪个维度的提问触发了最强回答）需要知道 A/B/C 谁在说。可用信号：自我介绍（“我是负责技术的四”）、面试通知里的面试官名单及其负责维度、提问领域与名单的匹配。

设计：身份区分是层 2 的**附加输出**，带 confidence；置信度低或信号缺失 → 归“面试官（未区分）”。**不阻断主流程**——因为 §0.2 说的边界：记错提问人污染的是评估者元数据，不影响对候选人的判断。

### 3.3 问答配对（含“谁问的”）

问题清单 × 转写段对齐，四分类：`asked_answered` / `asked_dodged` / `not_asked` / `ad_hoc`。每条附提问人身份（区分成功时）。`not_asked` 的归属不变：**面试官的遗漏，不是候选人的缺陷**，UI 分开呈现。

### 3.4 未来扩展：真正的群面（本期不做）

一个面试官 × 多个候选人时，出现 §0.7 的问题：区分候选人 A 和 B 在无声纹 embedding 下没有可靠自动解，而错标会把 A 的发言算到 B 头上，污染评分且无人发觉。届时正确做法是先引入声纹 embedding（违反零依赖约束，需产品决策），或退化为“候选人身份人工指派 + 未确认不计分”。本期不做，文档留此案。

## 4. 问答配对与面试分析

### 主张核对：三方交叉（Panel 下升级为多源）

| 信号源 | 作用 |
|---|---|
| 口头主张（转写） | 现场说的 |
| 简历书面主张 | 事前写的 |
| 面试官笔记记录 | 旁观者记的 |

矛盾即信号，且**三方比两方能定位偏差在哪一侧**：

- 简历“负责 X”，面试中说“参与 X”，笔记记“他主导了 X” → 三方矛盾，权重虚高信号最强
- 笔记打了高分的点，转写里找不到对应内容 → **笔记偏差**（面试官记住的 vs 实际发生的）
- 多位面试官的笔记相互矛盾 → **评估者间一致性**，这是评分系统最该收集的元数据，Panel 场景天然多源

### 回答证据锚定

回答挂在具体经历上（“在 X 项目用 Y 做 Z，结果 W”）vs 空泛表态（“我学习能力强”）——正方/反方辩论的现成原料，不需要新机制。

### 面试官图文记录（P2b）

- 新素材角色 `interviewer_notes`：粘贴文字 / 截图 / 手写笔记拍照，多人多份
- 图片走 `docparse.parse_image` 现成 OCR；文字直读
- 分析价值：上述三方核对的“第三方源”；每份笔记可关联到具体面试官（上传时署名，不依赖声纹归属——**署名比听声准，这是刻意选择**）
- 合规：笔记属评价记录 + 面试官个人信息，进权限控制与审计

| **P2a** | 主张核对三方版 + 覆盖度 + 证据锚定，写入 `interview_transcript` | 端到端跑通；埋入 fixture 的三方矛盾被标出 |
| **P2b** | 面试官图文记录：新角色、OCR 接线、多源笔记的评估者间一致性分析 | 笔记拍照上传 → OCR → 一致性分析；多位面试官笔记矛盾能被标出 |
| **P3** | UI：上传（音频+图文）、逐段归属修正、问答对照（含提问人维度）；PIPL 同意阻断；音频删除补缺 | 修正写审计；未同意阻断上传；test_viewer 无新死接口；`erase_person` 覆盖音频文件 |

**每期独立可交付**：P0 完就能转写；P1 完就能“谁在说、谁问了什么”；不憋大招。

### 测试策略（项目传统）

- **fixture 优先**：双人 + 三人 Panel 的 ground truth 转写是 P1 的地基
- **mock ASR/OCR 保留**：流程测试不依赖 faster-whisper 和视觉通道（可选/单通道依赖，CI 不装）
- **合规即测试**：“未同意阻断”进验收测试，不是文档承诺

## 6. 合规义务（PIPL）

| 义务 | 设计 |
|---|---|
| 录音告知同意 | 上传前强制勾选“已告知候选人并取得同意”，写审计；未勾选阻断 |

## 7. 对实习投递的价值（做到 P2）

讲稿可新增一个核心决策：**“说话人分离为什么不用 pyannote”**——零依赖约束下，用“已知问题清单对齐 + LLM 言语行为归因 + 人工终审”解决问题；且按场景分级（1:1 与 Panel 同机制全自动 / 群面明确不做并说明原因），每层带置信度，失败方向保守。这与你现有的“注入三层防护”“身份判定宁可漏合并”是同一套价值观。

外加两条面试官几乎必问的：**“多个面试官怎么区分谁在说”**（角色分离必须准，面试官身份尽力为准——因为记错提问人污染的是元数据不是判断，这个“影响面分级”的判断本身就是设计亮点）；**“为什么不做群面”**（无声纹下区分两个候选人没有可靠自动解，错了会污染评分且无人察觉——**敢于划定不做边界比假装全能更可信**）。
